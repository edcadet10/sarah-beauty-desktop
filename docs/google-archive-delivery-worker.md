# Deliver a saved encrypted archive

Status: The delivery worker is implemented. The recurring queue, desktop controls, and real Google account acceptance follow separately. Tests use real local encryption and an in-memory HTTP server; no real Google request occurs.

An owner can request delivery of a saved local archive. A background entry point uses the explicitly saved Drive output permission without touching a human session. An exclusive file lease prevents concurrent workers for the store. Only its holder marks the selected delivery's earlier Running attempts Interrupted/CompletionUnconfirmed.

The worker verifies the folder, reserves or reuses a durable Drive file identity, starts a separate attempt, and checks whether that remote file already completed. Existing verified completion needs no content write. Otherwise, it holds the local ciphertext against replacement, checks its complete hash/header, and uses the resumable transport. An already-existing identity is verified rather than overwritten.

Before each remote request, the access callback rechecks current policy, connection, recovery material, and source history. It can renew Google access without renewing a human session. After transfer, a separate file read verifies exact content/binding/private-access facts, and another folder read verifies current destination access. The final short local transaction checks authority again before recording success. Long hashing/network work holds no database writer reservation.

Cancellation or withdrawal after Google accepted content preserves the remote file and records a non-success outcome. The same reserved identity permits later verification without sending another copy. Missing local outcome persistence reports an unconfirmed state; it does not assert that the remote request never happened. Known hard authorization rejection persists the generation-bound reconnect requirement. Fixed failure history excludes provider messages, tokens, and private upload locations.

The worker does not create a new archive, start a timer, delete history, buy storage, share a file, or mark a second-device restore test complete. A pending later business watermark remains outside the delivered archive's exact captured coverage. Real account permissions and physical device/recovery acceptance still require their own checks.

Eight worker cases and seven history cases cover delivery (15 targeted cases). One creates actual bookkeeping, an issued PDF, and managed evidence, transfers the real encrypted archive through the actual HTTP transport against an in-memory server, checks exact received bytes, and decrypts/stages the received copy with matching watermark and source facts. Locked human access and the business watermark remain unchanged. Other cases verify retry without another content write, late withdrawal and later business changes, changed local bytes before any content request, remote group access, exclusive lease/interrupted-state recovery, and late cancellation. A failing-before regression showed cancellation after the earlier check could still record success; checking again inside the final writer transaction closes that boundary. This is a simulated-server integration check, not real Google or second-device acceptance.
