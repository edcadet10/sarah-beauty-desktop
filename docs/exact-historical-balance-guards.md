# Check historical balances with exact arithmetic

Historical nonnegative-balance guards now read integer journal lines and accumulate each date and running balance with `BigInteger`. Loan principal, owner reimbursement payable, tax liability and asset carrying-value checks keep their existing date-level rules and business/dimension filters. A negative date still rejects the proposed posting inside its transaction. Individual stored movements and journal lines still use integer cents.

Seven public-command probes failed before this change. Same-date positive histories overflowed SQLite's integer `SUM`; totals across dates and the signed-minimum credit-normal boundary overflowed the running `long` arithmetic. [SQLite documents](https://www.sqlite.org/lang_aggfunc.html#sumunc) that integer `sum()` can overflow during accumulation. The fix keeps the arithmetic exact without converting amounts to floating point or changing stored history.

Forty-four related cases pass: nine boundary/tax cases plus posting, ledger-report, asset-disposal, owner-schedule and tax-recovery checks. Large loan, owner-paid expense and asset histories work on one date or across dates. Valid tax remittance against a large positive liability succeeds; an earlier negative-date remittance and other invalid backdated postings still reject without another movement or watermark change. The Windows Debug build passes without warnings or errors.

This change is limited to historical nonnegative-balance guards. Public report totals still have their documented supported cent range; other financial aggregation paths require separate checks. The preceding discard-command regression passes 1,575 cases at `6010845`. Full regression for this change is running. Release and actual device/account acceptance remain pending.
