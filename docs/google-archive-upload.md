# Send an encrypted archive in resumable chunks

Status: The internal transfer component is implemented. Durable delivery attempts, destination permission integration, desktop controls, and real account acceptance follow separately. No real Google upload was performed.

The component first checks the source length, age-format header, and complete SHA-256 against supplied archive facts. The header detects accidental plaintext selection; it does not replace the existing archive encryption and recovery verification. Callers must retain a completed verified archive and prevent source replacement during delivery.

The transfer creates a new binary file using a pre-generated Drive file identity, generic archive/job name, the confirmed parent folder, and app/job/hash bindings. It does not overwrite earlier archives or request sharing. [Google documents pre-generated IDs](https://developers.google.com/workspace/drive/api/guides/manage-uploads#use_a_pre-generated_id_to_upload_files) as a way to retry uncertain creates without producing duplicate files. The delivery job must persist that ID before sending content and check existing remote completion when retrying.

The initiation bypasses domain-default visibility. Its private session address must use HTTPS, Google's exact upload host/path and default port, with no user information or fragment. The address stays in memory and has a redacted display. The default transport disables automatic redirects and cookies. Bearer material stays in headers; an access callback lets the delivery service recheck authority and obtain current access before every request.

Four-MiB chunks follow [Google's resumable upload protocol](https://developers.google.com/workspace/drive/api/guides/manage-uploads#perform_a_resumable_upload). The component advances only to acknowledged ranges, rejects missing/nonprogressing/backward/out-of-bounds progress, and queries actual status after an uncertain network/server response. Up to three status recoveries use one-, two-, and four-second delays. A lost final response can be confirmed without sending the archive again. Individual requests are bounded to sixty seconds; the complete transfer has a two-hour cancellable deadline.

Completion requires exact file identity, byte length, and [Drive SHA-256 checksum](https://developers.google.com/workspace/drive/api/reference/rest/v3/files). Missing or different facts remain unconfirmed. This transport result alone does not establish current folder privacy, durable local success, or a restore test. The delivery service must recheck authority and remote file/destination facts before recording success. Interrupted sessions and unconfirmed completed files are preserved for review; this component performs no remote deletion.

Eighteen fictional transport cases pass with account/folder transport cases (47 targeted cases). They cover exact two-chunk bytes, partial acknowledgment after an uncertain write, lost final response, untrusted locations, invalid progress, changed/missing completion facts, changed/plaintext sources, cancellation, generated IDs, and redacted session display. The initial run rejected valid-format fixtures because the header allocation was one byte short; deriving its length from the format bytes corrected the guard. Persistent retry and completion history follow separately.
